# Janus Technical Specification

This file is the canonical entrypoint for Janus technical specifications. Keep it concise: detailed requirements live in the child specs under [`docs/docs/tech-spec/`](docs/docs/tech-spec/), which are also exposed through the in-app documentation navigation.

## Project Overview

Janus is a private, passive AI assistant that helps users manage email, planning, and daily context without compromising privacy. It monitors communications, synchronizes with productivity tools, and presents an AI-driven overview through a web dashboard, CLI, and native iOS client scaffold.

## Ownership And Update Rules

1. Update the relevant child technical spec before or with any significant behavior, architecture, schema, security, deployment, frontend, mobile, worker, LLM, or agent-tool change.
2. Update this index only when the map, summaries, or ownership guidance change.
3. Preserve root-to-child links and the in-app docs navigation when adding or moving child specs.
4. Keep implementation details out of this landing page unless they explain where to find the authoritative child spec.
5. Documentation is a delivery artifact, not a follow-up: a change is not review-ready until the affected child spec(s), feature-spec/planned-feature page(s), and user-facing docs reflect the new state. See [`delivery-artifacts.md`](docs/docs/tech-spec/delivery-artifacts.md) for the Status/Linear/Depends-on convention that planned-feature docs must follow.

## Development Mandates

1. **Spec First:** Any significant change or new feature must be preceded by a proposed update to the relevant technical-spec document(s) and, when needed, this root index.
   - Any change backed by a Linear issue that also has a `docs/docs/features/planned/` or `docs/docs/feature-specs/` page must update that page's Status/Linear/Depends-on block per [`delivery-artifacts.md`](docs/docs/tech-spec/delivery-artifacts.md) in the same change — do not ship a feature while its doc still says `Planned`.
2. **Map First:** Contributors and coding agents should read the root [`CODEMAP.md`](CODEMAP.md), then the nearest child `CODEMAP.md`, before opening implementation files.
3. **Component Dissection:** No monolithic pages. Pages should be compositions of small, testable components.
4. **Data Integrity:** Backend routes, services, and tools must verify data ownership and session validity for all requests.
5. **Local First:** Prioritize local execution through SQLite, Ollama-compatible local models, and encrypted local credentials wherever practical.
