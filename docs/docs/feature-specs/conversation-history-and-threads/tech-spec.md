# Tech spec: conversation history and threads

## Status

Question-driven draft. This document intentionally does not fill in behavioral gaps without user confirmation.

## Confirmed requirements

1. The chat conversation should be stored in the database.
2. The product should support multiple conversations.
3. The user should be able to start new conversations and continue old ones.
4. The conversation title should be autogenerated directly after the first prompt.

## Open questions for user confirmation

1. Should titles be generated from only the first user prompt, or from the first assistant response as well?
2. Can users rename conversation titles manually after auto-generation?
3. Should deleting conversations be part of the first release?
4. Should conversations be scoped per authenticated user only, or is any shared/admin visibility expected?
5. How much message history should be loaded by default when reopening a conversation?
6. Should a conversation remember the exact planner/mail context snapshot used when each assistant response was generated?
7. Should title generation happen synchronously after the first prompt, or asynchronously shortly afterwards?

## Technical decision areas

1. **Schema shape**
   - conversation table
   - message table
   - user ownership
   - timestamps
   - selected agent definition reference *(no longer applicable: agent definitions were removed in JAN-227; conversations have no agent reference)*
2. **Title generation**
   - LLM-generated title
   - rule-based fallback title if LLM is unavailable
3. **Message persistence timing**
   - persist partial streamed assistant output incrementally
   - or persist only finalized assistant messages
4. **Resume semantics**
   - whether resuming a conversation reconstructs prior context from stored messages only
   - or also restores stored tool/resource scope and other metadata

## Proposed spec structure once questions are answered

1. Data model
2. API shape
3. Persistence timing for user and assistant messages
4. Title-generation workflow
5. Conversation list and resume semantics
6. Retention, deletion, and limits
7. Acceptance criteria and tests

## Initial acceptance criteria candidates pending confirmation

1. Every chat message belongs to a persisted conversation.
2. New conversations can be started explicitly.
3. Existing conversations can be resumed without losing prior message history.
4. A title is created automatically after the first prompt, with a documented fallback path if generation fails.
