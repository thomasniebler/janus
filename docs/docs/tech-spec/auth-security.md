# Authentication and Security Model

## Authentication

- **JWT via cookies and headers:** Janus prefers secure, HTTP-only cookies for dashboard authentication and `Authorization` headers for CLI/API usage.
- **Dependency strategy:** `get_current_user` is strict and raises `401 Unauthorized` if authentication fails. `get_user_or_none` is permissive and returns `None` if authentication fails.
- **Device tokens (action inbox):** a script or device that cannot hold a browser session uses a scoped, revocable device token, `Authorization: Bearer jdt_...`. `security.get_token` parses every bearer as a JWT, so an opaque device token fails there and every endpoint that uses `get_current_user` answers 401; only `api/inbox.py`'s `get_inbox_user` also resolves it, through `DeviceTokenService.authenticate`, and only when no valid web session is present (a cookie wins). The plaintext is returned once by `POST /api/inbox/tokens` and never stored: `device_tokens` holds its SHA-256 (`token_hash`, unique), a display prefix, `last_used_at` (written at most once a minute) and `revoked_at`. At most ten active tokens per owner. `AuthService.change_password` and `revoke_user_sessions` call `DeviceTokenService.revoke_all`, and `DELETE /api/auth/users/{username}` calls `delete_all` (SQLite may reuse a deleted user's id, so a leftover row could authenticate as the next user). A valid web session wins; when it is missing or invalid, a device token in the `Authorization` header is tried (`get_inbox_user`). Creating, listing, and revoking tokens needs the web session, so a device token cannot mint or revoke tokens. A device token may take only the inbox actions `mark_read` and `dismiss` (`inbox_service.ACTIONS`); approvals (trigger proposals, character state, suggestions, clarifications) stay web-session only. Cookie sessions keep CSRF protection on the inbox actions; a bearer-only request has none to protect. Covered by `tests/test_inbox.py` and `frontend/e2e/device-access.spec.ts`.
- **Context awareness:** `get_user_or_none`/`get_current_user` resolve the token through `get_token`, which reads the `Authorization` header and `access_token` cookie via plain FastAPI `Header`/`Cookie` parameter injection — a mechanism that already works uniformly for both HTTP requests and WebSocket handshakes, so no dependency needs to accept `Request`/`WebSocket` explicitly. `/ws/chat`, `/ws/briefing` and `/ws/changes` depend on `security.get_websocket_user_or_none`, which runs the same `get_user_or_none` check on its own short-lived session, closes it, and returns the user detached (JAN-336): a dependency's `Depends(database.get_db)` session is only torn down when the endpoint returns, which for a socket is when it closes, so authenticating through it pinned one pooled connection per open socket, next to the handler's own, and a few open tabs exhausted the pool (`QueuePool limit ... reached`). `/ws/chat` attaches the user to its handler's session with `merge(load=False)` and ends that session's transaction before waiting for each message, so an idle chat socket holds no connection and the checked-out count is bounded by the turns in flight, not the open tabs; `tests/test_websocket_db_sessions.py` covers this against a real `QueuePool`. `/ws/changes` additionally re-validates the session before every heartbeat and closes with 1008 once it is logged out or revoked (JAN-104).
- **Admin enforcement:** `admin_required` wraps `get_current_user` to check the `is_admin` flag.
- **Instance-wide settings are admin-only to change (JAN-222):** every user may read them, but only an admin may write the shared `Settings` row: `PATCH /api/planner/settings`, `PATCH /api/web-search/settings`, `PATCH /api/github/settings`, `PATCH /api/linear/settings`, and `PATCH /api/emails/settings` (the mail sync limit), plus `POST /api/planner/test-llm` and `POST /api/planner/llm-models`, which run with the stored keys. The Settings cards for them (`LLMConfig`, `WebSearchConfig`, `GitHubConfig`, `LinearConfig`, `MailIngestionConfig`) are read-only for a non-admin.
- **A stored LLM key only goes to its own base URL (JAN-222):** a model lookup or connection test with a draft base URL and no draft key never sends the stored key there; the test answers `Enter the API key to test this base URL…` without calling out (`llm_model_catalog.resolve_credentials` and `draft_withholds_stored_key` decide).

## Password Hashing

- **Direct bcrypt:** `security.SecurityService` hashes and verifies passwords with the `bcrypt` package directly (`bcrypt.hashpw` / `bcrypt.checkpw`, cost 12, `$2b$` format); there is no passlib layer. Hashes written by the earlier passlib + bcrypt<4 stack use the same `$2b$` format and verify unchanged, so no rehash migration is needed.
- **72-byte limit — reject, don't pre-hash:** bcrypt only covers the first 72 bytes of its input, and bcrypt>=5 raises instead of silently truncating. Janus rejects any *new* password longer than 72 UTF-8 bytes: the password-setting schemas (`UserCreate.password`, `PasswordChangeRequest.new_password`, `InitialSetupRequest.password`) return `422`, and `get_password_hash` raises `ValueError` as a backstop for non-API callers such as `janus user bootstrap-admin`. Pre-hashing (e.g. HMAC-SHA256 before bcrypt) was not chosen because it changes the stored hash format and would need a legacy-verification fallback.
- **Legacy compatibility on verify:** `verify_password` truncates input to 72 bytes before checking, reproducing how the old stack hashed over-long passwords, so users who set one before the switch can still log in by typing it in full. A stored value that is not a valid bcrypt hash verifies as `False` rather than raising.

## First-Run Setup

- If the database has no users, Janus must not create default credentials.
- Janus supports two bootstrap paths for the first admin account: a local SSH/CLI command that writes the first admin directly, and an optional public browser setup flow.
- When `public_setup_enabled` is true, startup prints a one-time setup token, `GET /api/auth/setup` reports whether setup is still required, and `POST /api/auth/setup` creates the first admin account and invalidates that token.
- When `public_setup_enabled` is false, public setup endpoints are unavailable and operators must bootstrap over SSH/CLI.
- The web client fetches setup status once per page load, treats the disabled endpoint's 404 as "no setup required", and does not refetch that answer on window focus (a refetch of a data-less query used to unmount the whole app shell, JAN-182). While setup is still required it refetches on focus, so an open `/setup` tab notices when another tab or the CLI created the first admin.
- Hosted deployments may disable the public setup surface and bootstrap the first admin over SSH/CLI instead.
- The `/setup` form shows the backend's reason when setup is refused (for example `Setup token is invalid or has expired.`), never axios's generic status text (JAN-218).
- `frontend/e2e/setup.spec.ts` drives this whole flow against a second, user-less backend with public setup on: every route leads to `/setup`, a wrong token or mismatched passwords are refused, the token printed in the startup log creates the admin, who then signs in to the dashboard, and the token cannot be replayed (JAN-218).

## Session Revocation and Abuse Resistance

- **Server-side session revocation:** Logout, password changes, and explicit admin session revocation must invalidate affected JWT-backed sessions on the server before their normal expiry.
- **Public deployment requirement:** A signed token with only an expiry is not sufficient as the sole revocation mechanism for public deployments.
- **Auth abuse resistance:** Login and optional public first-run setup endpoints must throttle repeated failed attempts by client IP and submitted username.
- **Audit visibility:** Failed and throttled attempts must be written to audit-friendly logs.
- **Expired revocation pruning:** auth flows opportunistically delete expired `RevokedSession` rows at a bounded interval and always commit that delete, even when it matched nothing: the statement alone holds SQLite's write lock, and leaving it open made the failed attempt's own audit event (written on another connection) stall for the busy timeout and then be dropped with `database is locked` (JAN-218).

## Proxy, Host, Origin, and Cookie Policy

- **Trusted reverse proxies:** Hosted deployments may trust forwarded scheme/host headers from a configured number of reverse-proxy hops so secure cookies, OAuth callback URLs, and same-origin redirects reflect the public HTTPS origin instead of the internal backend listener.
- **Production cookie policy:** For HTTPS deployments, dashboard auth cookies must always be `Secure` and `HttpOnly`, with the secure decision based on the effective external/public request scheme after trusted proxy headers are applied.
- **Host allowlist:** Janus validates incoming `Host` headers against an explicit configured allowlist after applying trusted forwarded-host reconstruction, and rejects unexpected hosts before normal route handling.
- **Origin allowlist:** Browser-facing deployments must set `allowed_origins` to the exact public dashboard origins. Janus uses that allowlist for both HTTP CORS responses and WebSocket `Origin` validation.
- **CSRF protection:** Mutating HTTP routes that rely on dashboard cookie sessions must require a valid CSRF signal bound to that authenticated session, while header-based API clients remain exempt. Inbound webhook deliveries (`/api/webhooks/in/`, `security.CSRF_EXEMPT_PREFIXES`, JAN-406) are exempt by path: they are authenticated by the endpoint's HMAC signature, never by the session, so a stray cookie on the sender must not refuse them.
- **Inbound webhooks (JAN-406):** `POST /api/webhooks/in/<key>` is public and authenticated by an HMAC-SHA256 signature with the endpoint's secret.
  - Signature styles: timestamped `X-Janus-Signature` (5-minute window), or GitHub's `X-Hub-Signature-256`; both compared in constant time.
  - Storage: the URL key is stored only as its SHA-256 hash, and the secret Fernet-encrypted; both are shown once.
  - Limits: 64 KB JSON bodies and 60 deliveries a minute per endpoint.
  - The route is a triaged Semgrep `janus-route-without-auth-dependency` exception. See [Inbound Webhooks](../feature-specs/inbound-webhooks.md).
- **WebSocket origin checks:** WebSocket handshakes must validate the `Origin` header against configured allowed origins before accepting dashboard sessions.

## Public Surface and Headers

- **Security headers:** HTTP responses include production-safe defaults for Content Security Policy, frame protections, `X-Content-Type-Options`, and `Referrer-Policy`.
- **Default-closed public surfaces:** Non-essential public surfaces stay disabled unless an operator explicitly enables them. Interactive API docs/OpenAPI exposure are off by default, and the browser-based first-run setup flow is opt-in.
- **Public surface minimization:** Production mode should disable or strictly protect non-essential public surfaces such as interactive API docs and setup endpoints that are no longer needed after provisioning.
- **In-app documentation needs a login (JAN-299):** `/api/docs/*` (user guides, tech specs, and the security assessments under `reviews/`) is served only to an authenticated session; unauthenticated requests get `401`. The public Zensical site, if an operator publishes one, is the place for public docs.

## Tenant Isolation

- **Ownership in the service layer:** user-owned rows (email accounts, rules, emails, conversations; knowledge sources, planner accounts, and WhatsApp accounts since JAN-288) are read and mutated through `*_for_user` service methods that filter on the owner in the same query. A foreign id answers exactly like a missing one (`404` from a router, `not found` from a tool), so its existence is never disclosed (JAN-137). See [Backend and API](backend-api.md) for the rule.
- **Mail is owned through its account:** an email belongs to the owner of the account it arrived on, and an email with no account has no owner. The dashboard email widgets, the briefing's email context, and the mail agent tools (`search_emails`, `get_email_detail`, `get_email_details_batch`) all start from `EmailService.query_emails_for_user`, so neither chat nor an unattended run (trigger, automation, delegated child) can read another user's mail by search or by id (JAN-286).
- **Outgoing mail uses the owner's own account:** `send_email` only sends from the run owner's own active account. Another user's account id is "not found", and when no `account_id` is given only the owner's accounts are considered (JAN-286).
- **Rule learning is per owner:** correction-derived rule creation and approved clarification suggestions only match, reorder, or retire the acting user's own rules (JAN-287).
- **Rules and accounts always have an owner (JAN-338):** `rules.user_id`, `email_accounts.user_id`, and `planner_accounts.user_id` are `NOT NULL` in the models and the migrations alike. Migration `37b30d7c85e1` gave rows from before ownership to the first admin and fails the upgrade when no admin exists, so no migrated database holds an ownerless rule or account, and nothing applies one user's row to another user's data.
- **Rule evaluation is per owner:** the IMAP rule evaluator (`EmailProcessor._evaluate_rules`) only applies the rules of the mail's owner, i.e. the owner of the account it arrived on, the same scope rule learning uses (JAN-287). Another user's rule never classifies, files as SPAM/IGNORE, or keeps from `mail.received` triggers someone else's mail. Mail handed to the processor without a known account is attributed like the rest of the ingestion pipeline (the first user); with no users at all no rule applies (JAN-295, JAN-338).
- **Agent calendar and task tools are per owner:** `list_calendar_events`/`get_event_detail` (`agent_toolboxes/calendar.py`) read only events of the run owner's planner accounts plus the synthetic reminder events of the owner's own reminders (owned through the reminder's source email account), and `list_tasks`/`get_task_detail` (`agent_toolboxes/tasks.py`) only tasks of the owner's planner accounts, in chat and in every unattended mode. Another user's event or task id answers "not found". Found by the Semgrep `janus-unscoped-owned-row-lookup` rule (JAN-267).
- **Reminder memory and the planner outlook are per owner:** reminder memory has no owner column; a reminder belongs to the owner of its source email's account, the same derivation domain-change notifications use. `ReminderService.get_active_reminders`, `get_preparation_outlook`, and `build_email_context` take the owner's id, so the context fed to reminder and topic extraction, the briefing's reminder and outlook sections, the planner context, and the reasoning prompt for a user's IMPORTANT correction only contain that user's reminders and the events of that user's own planner accounts. A reminder whose source email has no account owner, or was purged, is shown to nobody until mail from the same account refreshes it. Dedupe never rewrites or re-points another user's reminder. Mail topics are captured for the mail's owner, not the first user (JAN-296).
- **Background mail notifications follow the mail's owner:** whether an incoming IMPORTANT email triggers a notification is decided by the `NotificationPreference` of the mail's owner (the receiving account's owner, attributed like the rest of the ingestion pipeline), never by the first user's. One user muting or filtering notifications never suppresses or enables another user's (JAN-298).

## Data and Prompt Safety

- **Regex safety:** User-defined rules are compiled and matched with `re2` so rule evaluation remains deterministic and protected from catastrophic backtracking.
- **Microsoft 365 sign-in:** Janus reaches Outlook and Teams through Microsoft Graph with *delegated* permissions, using its own Entra ID app registration (`JANUS_MICROSOFT_CLIENT_ID`, `JANUS_MICROSOFT_TENANT_ID`) and MSAL's `PublicClientApplication` (`services/microsoft_auth_service.py`). It does not use `DefaultAzureCredential` for Graph: that chain would pick an `az login` token, which carries only the permissions Microsoft pre-consented for the Azure CLI's own app and lacks the Teams and mail scopes. Sign-in is a one-time local browser flow (`janus microsoft login`, `acquire_token_interactive`, 5 minute timeout); every other call is `acquire_token_silent`, so background code never opens a browser and an expired sign-in is an error that names the login command. MSAL's token cache (including the refresh token) is serialized, encrypted with the Fernet key through `security.security_service`, and written to `<data dir>/microsoft_token_cache.enc` (mode `0600`) only when MSAL changed it (refresh tokens rotate). `azure-identity`'s persistent cache was rejected because on Linux it needs libsecret through PyGObject, which a `uv` environment does not have, and its only fallback is a plaintext file. A cache that cannot be decrypted (changed key) reads as signed out with an actionable error. The token is requested with the `.default` scope, so a permission that was not consented fails at the tool call with a Graph 403 instead of failing the sign-in. The connection is one identity per instance, usable only by administrators (see [Microsoft 365 tools](llm-agent-safety.md#microsoft-365-tools-microsoft)).
- **Prompt injection guardrails:** Email content passed to any LLM prompt must be wrapped in `<email_content ...>` tags, HTML-escaped, and preceded by an instruction that content inside those tags is untrusted external data. Tool output from toolboxes that return outside content is spotlighted, scanned for injection patterns, and escalates consequential tools after a detection; see [Prompt-injection guardrails](llm-agent-safety.md#prompt-injection-guardrails-jan-127).
- **Provider-specific AI secrets:** API keys for cloud LLM backends are stored encrypted at rest and are never returned directly in normal settings responses. The frontend only receives configured booleans for those secrets.
- **Credential encryption:** Sensitive credentials are stored encrypted at rest through the configured Janus security service and local Fernet key.

## Dependency Vulnerability Audit

`scripts/dependency_audit.py` (`task audit:deps`, JAN-268) checks the pinned dependencies for known vulnerabilities. The `Dependency audit` workflow runs it daily on `main`, because advisories are published without any code change. On pull requests, CI calls the same workflow when the PR changes a dependency definition or lockfile (`pyproject.toml`, `uv.lock`, the root, `frontend/` or `modules/` npm manifests and lockfiles), the audit script, its exceptions in `pyproject.toml`, `Taskfile.yml`, or the workflow (JAN-313, [CI job selection](architecture-overview.md#ci-job-selection)); a PR that changes none of them skips the audit, and the job summary says why. It reports and blocks; it never upgrades anything.

- **Python:** `uv export --frozen` writes hashed requirements from `uv.lock` for five separate scopes: production (`--no-dev`), the dev group (`--only-dev`), and the optional `documents`, `whatsapp`, and `desktop` extras. `pip-audit` (pinned to 2.10.1, run through `uvx`) checks each scope without resolving or installing anything. pip-audit's PyPI/OSV data carries no severity, so every Python finding blocks.
- **npm:** `npm audit --package-lock-only` runs over every lockfile in scope: the root `package-lock.json` (Tailwind CSS for the server-rendered pages), `frontend/` (the React dashboard), and `modules/todo-chat/frontend/` (the todo-chat desktop module). High and critical findings block; moderate and low ones are reported only. A second `--omit=dev` pass labels each finding production or dev.
- **Report:** every finding lists ecosystem, package, version, advisory id with aliases, severity, the available fix, and the scopes it affects. It is printed, written to the job summary, and uploaded as the `dependency-audit` JSON artifact. A scanner that cannot run (network, lockfile, tool failure) exits 2 and fails the job rather than passing silently.
- **Exceptions:** an accepted finding is a `[[tool.janus.dependency_audit.exceptions]]` entry in `pyproject.toml` with the advisory `id` (any alias matches), the `package`, a `reason`, and an `expires` date. An expired entry, or one that no longer matches a finding, fails the audit, so exceptions are time-limited and cannot go stale.
- **Fixing a finding:** upgrade only the affected package to the smallest fixed release, as a reviewed lockfile change (`uv lock --upgrade-package <name>==<version>`, or `npm install <name>@<version>` in the project directory). Dependabot (`.github/dependabot.yml`) keeps proposing routine bumps separately, as one weekly grouped version-update PR for uv/npm (`weekly-dependencies`) plus one for GitHub Actions.

## Static Security Scan (Semgrep)

`scripts/semgrep_scan.py` (`task security:semgrep`, JAN-267) runs Semgrep over `src/`, `frontend/src/`, and `scripts/`. The `Semgrep` workflow scans all of `main` weekly and on manual dispatch, and uploads SARIF and JSON reports as the `semgrep` artifact. On pull requests, CI calls the same workflow when the PR changes scanned source (`src/`, `frontend/src/`, `scripts/`), `.semgrep/`, `.semgrepignore`, the scan wrapper, `pyproject.toml` (pins and exceptions), `uv.lock`, `Taskfile.yml`, or the workflow, and whenever a path is unmapped (JAN-313, [CI job selection](architecture-overview.md#ci-job-selection)). A docs-only or agent-only PR skips it, and the job summary says why. No finding is suppressed to save time. It reads source only and never probes a running Janus; it complements, and does not replace, the live penetration test (JAN-238).

- **Reproducible rules:** Semgrep is pinned (`semgrep==1.179.0`), and the community rules come from `semgrep/semgrep-rules` at a pinned commit, fetched into `.cache/semgrep-rules`, never from the registry, whose packs change without notice. Only security-relevant rule directories are used: Python `lang/security`, FastAPI, JWT, SQLAlchemy, requests, cryptography, Jinja2; JavaScript/TypeScript browser, `lang/security`, React, `jsonwebtoken`; and generic secrets. Bumping the pin is a reviewed change.
- **Janus rules (`.semgrep/janus.yml`):** `janus-route-without-auth-dependency` flags an API route with neither `Depends(security.get_current_user)` nor `Depends(security.admin_required)`, on the route or its router. `janus-websocket-without-auth-dependency` flags a WebSocket handler registered with `api.websocket(...)(handler)` that has none of `Depends(security.get_websocket_user_or_none)`, `Depends(security.get_user_or_none)` or `Depends(security.get_current_user)`. `janus-unscoped-owned-row-lookup` flags `db.get(models.<Model>, id)` on a user-owned model in routers, toolboxes, and WebSocket handlers, where the owner-scoped `*_for_user` lookup belongs (see Tenant Isolation). The scan first runs `semgrep --test` against the annotated fixture `.semgrep/janus.py`, so a rule that stops matching fails the scan.
- **Severity policy:** INFO rules are not run. ERROR findings block; WARNING findings are reported only. Test files, stories, fixtures, and generated clients are skipped (`.semgrepignore`). A partial parse is tolerated (Semgrep still scans the rest of the file); any other scanner error fails the run.
- **Triage and exceptions:** an accepted finding is a `[[tool.janus.semgrep.exceptions]]` entry in `pyproject.toml` with the `rule`, the `path`, an optional `line` text that must appear in the flagged line, a `reason`, and an `expires` date. An expired entry, or one that no longer matches a finding, fails the scan, so every exception is re-triaged before it lapses. The action inbox's two routes that authenticate through `get_inbox_user` (a web session or a scoped device token) instead of `get_current_user` are excepted with their reason (`api/inbox.py`). The initial baseline (public auth and OAuth routes, the health probe, ORM-derived SQL identifiers, the timing-equalizing dummy bcrypt hash) is triaged there. The shell tool's `subprocess.Popen` (`dangerous-subprocess-use-audit` in `services/shell_service.py`, JAN-353) is excepted too: running a command is the tool's purpose, and its fences (operator opt-in, admins only, exact per-call approval, no shell by default, scrubbed environment, limits) are in [LLM and agent safety](llm-agent-safety.md#shell-shell-jan-353). Self-hosted auto-update's `subprocess.run` and `os.execv` (`dangerous-subprocess-use-audit`, `dangerous-os-exec-audit`, `dangerous-os-exec-tainted-env-args` in `services/update_service.py`) are excepted as well: the commands are fixed install steps and the re-exec reuses the operator's own `janus start` argv; the only value from GitHub, the release tag, is validated as `vX.Y.Z` and reaches `git` only; a tool install passes `uv tool install`/`pipx install` a local wheel path named from that validated version, after the download matched its published SHA-256 ([self-hosted auto-update](deployment-operations.md#self-hosted-auto-update)).
