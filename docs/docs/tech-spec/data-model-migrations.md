# Data Model and Migrations

## Persistence Baseline

- Janus stores durable application state in SQLite (default) or PostgreSQL through SQLAlchemy ORM models; `janus db copy` moves an existing database from one backend to the other.
- **SQLite concurrency (JAN-382):** one process runs many threads against the same file (trigger worker, chat, IMAP monitors, the vector index), so every engine built by `database.create_app_engine` for an on-disk SQLite URL sets `journal_mode=WAL`, a 30 s `busy_timeout` (also the driver's `timeout`), and `synchronous=NORMAL` on each new connection. In-memory databases are left alone. WAL adds `janus.db-wal` and `janus.db-shm` next to the database: back it up with SQLite's online backup API (as `scripts/pre_release_snapshot.py` does) or copy all three files while stopped, never `janus.db` alone. `tests/test_database_concurrency.py` covers the pragmas and concurrent writers.
- Schema changes are managed through Alembic migrations. **The models and the migrations must describe the same schema (JAN-338):** `tests/test_database_migrations.py::test_migrated_schema_matches_the_orm_models` upgrades a fresh SQLite database to head, runs Alembic's autogenerate comparison (`compare_metadata`, `compare_type=True`, the `knowledge_fts_*` tables excluded as in `alembic/env.py`) and `alembic check`, and fails on any difference, so a model change without its migration (or the reverse) fails the test suite.
- **Where the models live (JAN-136):** the `janus.models` package (`src/janus/models/`) holds one module per domain: `enums` (shared enums), `users`, `agents` (`CharacterProfile`, `AgentSkill`), `email`, `planner`, `whatsapp`, `reminders`, `topics`, `conversations`, `events`, `triggers`, `delegation`, `memory`, `auth`, `settings`, and `mcp`. The older feature modules `models_character.py`, `models_images.py`, `models_knowledge.py`, `models_safety.py`, `models_self_evolution.py`, and `models_toolsets.py` stay next to it. `janus/models/__init__.py` imports every module and re-exports every name, so `from janus import models` / `models.X` and `from janus.models import X` work as before, and `alembic/env.py` (which reads `models.database.Base.metadata`) sees the full model set. A new model goes into its domain module (or a new one, imported and re-exported from `__init__.py`); every module uses `janus.database.Base`. The split changed no table, column, constraint, or index, so it has no migration.
- Sensitive credentials are encrypted at rest.
- **Timestamps are UTC (JAN-394):** every `DateTime` column holds naive UTC. Writers convert aware values with `time_utils.to_naive_utc` before storing (SQLite keeps an aware value's wall time and drops its offset). The API returns these values without an offset, so clients read an offset-less timestamp as UTC and render it in the viewer's local time (the frontend's `parseServerDate`); Janus's own tools get them with an explicit `+00:00` (`agent_toolboxes.shared.iso`).
- User-scoped data must include enough ownership information for backend routes and tools to enforce access boundaries.
- **Knowledge layer:** phase 1 (JAN-241) stores embeddings for memory facts and tracked topics, and phase 2 (JAN-242) adds ingested sources and their chunks (below); later phases add entities, relations, and wiki pages on top of SQLite, which stays the production backend. See [`knowledge-graph-and-wiki.md`](../feature-specs/knowledge-graph-and-wiki.md).

## Durable Feature Models

- **Email records:** Stored messages include classification, confidence, reasoning, and state needed for dashboard display and manual reclassification.
- **Clarification queue:** Learned rule candidates store the corrected email, previous and requested priority, suggested rule, confidence, and explanation.
- **Planner state:** Planner sync records include freshness and error state used by dashboard summaries and status pages.
- **Local planner domain:** Janus-owned `PlannerTask`, `PlannerEvent`, `PlannerSuggestion`, and `PlannerLink` tables persist writable planner state, review queues, and evidence links separately from imported planner tables.
- **Status events:** Recent service degradations, outages, and recoveries are persisted as structured status events.
- **Reminder memory:** Derived reminders persist as active memory and are mirrored into Janus-managed calendar-style entries. `reminder_memory` has no owner column: a reminder is owned through its source email's account (`source_email_id` → `emails.account_id` → `email_accounts.user_id`), and every read filters on that owner (JAN-296).
- **Durable memory facts:** Memory facts include user ownership, summary, optional detail, provenance metadata, lifecycle state, and timestamps.
- **Knowledge embeddings (JAN-241):** `KnowledgeEmbedding` (`knowledge_embeddings`) holds one little-endian float32 `vector` per memory fact or tracked topic (`owner_type` `fact`/`topic` + `owner_id`, unique together, no FK because the owner is polymorphic; the flush hook in `services/knowledge_index.py` deletes the row with its owner), with `user_id` (FK, `ON DELETE CASCADE`), `model` (`provider/model`), `dimensions`, `content_hash`, `source_updated_at` (the owner's `updated_at` at embedding time), and `embedded_at`. A row is stale when its model differs from the configured one or its owner changed. `Settings.embedding_provider`/`embedding_model` (nullable; `NULL` = embeddings off) and `embedding_min_similarity` (default `0.5`) configure it.
- **Knowledge sources and chunks (JAN-242, `models_knowledge.py`):** `KnowledgeSource` (`knowledge_sources`) is one ingested unit per user: an email, an email attachment, a chat conversation, a WhatsApp chat, a calendar event, a planner task, or an uploaded file (`source_type`, a string), keyed by `(user_id, source_type, owner_id, part)` (unique; `owner_id` is the Janus row it came from, `NULL` for uploads, and `part` numbers the attachments of one email). It carries `title`, `mime_type`, `size_bytes`, `content_hash` (of the extracted text), `status` (`pending`/`ready`/`skipped`/`failed`) with `status_detail`, `attempts`, `source_updated_at`, `processed_at`, and `staged_content`: the raw bytes of an attachment or upload that has not been parsed yet, dropped once it is parsed or fails for good. Only extracted text is kept. `KnowledgeChunk` (`knowledge_chunks`) holds a source's text in order (`source_id` FK `ON DELETE CASCADE`, `user_id`, `ordinal` unique per source, `text`, `content_hash`, `char_count`, `token_estimate`); chunks are embedded as `knowledge_embeddings.owner_type = "chunk"`. SQLite does not enforce the cascades here, so `services/knowledge_sources.py` deletes chunks and their vectors explicitly.
- **Knowledge graph (JAN-243, `models_knowledge.py`):** `KnowledgeEntity` (`knowledge_entities`: `entity_type` person/organization/project/place/product/concept, `name`, `normalized_name` unique per `(user_id, entity_type)`, JSON `aliases`, `description`); `KnowledgeMention` (`knowledge_mentions`, chunk ↔ entity, unique per pair); `KnowledgeRelation` (`knowledge_relations`, `subject_id`/`predicate`/`object_id` unique, `confidence` high/medium, `valid_from`/`valid_to`) with `KnowledgeRelationEvidence` (`knowledge_relation_evidence`, relation ↔ chunk); `KnowledgeMergeSuggestion` (`knowledge_merge_suggestions`, `entity_id`/`duplicate_id` unique, `reason`, `status` pending/rejected; an accepted suggestion is deleted with the merged duplicate); `KnowledgeLlmUsage` (`knowledge_llm_usage`, input/output tokens and calls per user and `YYYY-MM`); `KnowledgePreference` (`knowledge_preferences`, per-user `monthly_token_budget`, default 2,000,000, created on the first save). `knowledge_chunks.extracted_hash` records the `content_hash` last extracted. Entities are embedded in `knowledge_embeddings` as `owner_type = "entity"` (no schema change). FKs are `ON DELETE CASCADE`, but SQLite does not enforce them, so `services/knowledge_graph.py` deletes explicitly.
- **Wiki (JAN-244, `models_knowledge.py`):** `WikiPage` (`wiki_pages`: `slug` unique per user, `title`, `subject_type` topic/entity and nullable `subject_id`, published Markdown `body`, JSON `citations` snapshots `{n, chunk_id, source_id, source_type, title, date}` (a marker citing a memory fact stores `fact_id` and `source_type: "memory_fact"` instead of `chunk_id`/`source_id`, JAN-334; no migration, the column is JSON), `input_hash`, `synthesized_at`, `checked_at` (last staleness check, oldest scanned first), `user_edited`) and `WikiPageRevision` (`wiki_page_revisions`: every published version and every proposal, with `author` janus/user/agent, `kind` published/proposed, proposal `status` pending/accepted/dismissed, `note`, `input_hash`). SQLite does not enforce the cascades; `services/wiki_service.py` deletes revisions with their page.
- **Runtime-managed keyword tables:** on SQLite builds with FTS5 (not the production host, whose keyword search falls back to substring matching), the FTS5 virtual tables `knowledge_fts_fact` and `knowledge_fts_topic` (rowid = owner id, `user_id UNINDEXED`) are created and backfilled at startup or on first use and kept in sync by the ORM flush hook. They are not Alembic-managed (`alembic/env.py` excludes `knowledge_fts_*` from autogenerate) and can be dropped at any time; they rebuild from the owner tables.
- **Device tokens (action inbox):** `DeviceToken` (`device_tokens`) has `user_id`, `name` (`String(80)`), `token_hash` (`String(64)`, unique, SHA-256 of the token), `token_prefix` (display only), `created_at`, `last_used_at`, and `revoked_at`; a revoked token stays as a row. Revision `d1a7c3e5f9b2` (revises `c9e3a5b7d1f2`) creates it.
- **Proactive secretary:** `NotificationPreference` (`notification_preferences`) has `secretary_active_start_hour` (`Integer`, default 8), `secretary_active_end_hour` (`Integer`, default 21, exclusive), `secretary_whatsapp_enabled` (`Boolean`, default off), `secretary_whatsapp_number` (`String`, nullable, stored as `+digits`), and `secretary_planner_fingerprint` (`String(64)`, nullable, the change gate's planner hash at the last real run, not an API field); `WhatsAppMessage` (`whatsapp_messages`) has a nullable, indexed `origin_trigger_id`, set on an outgoing message an unattended run sent itself and counted for the daily alert cap. Revision `c9e3a5b7d1f2` (revises `b7d2e4a6c8f1`) adds them.
- **Janus-started conversations (JAN-319):** `Conversation` (`conversations`) has `origin` (`String(16)`, `user`/`janus`, server default `user`), nullable indexed `origin_trigger_id` (the `RuntimeTrigger.trigger_id` of the run that started it), and `unread` (boolean, server default false), added by migration `d7f9b1c3e5a7`. See [background workers runtime](background-workers-runtime.md), "Janus-started conversations".
- **Chat tool calls (JAN-249):** `ConversationToolCall` (`conversation_tool_calls`) stores the final state of each tool call an assistant `ConversationMessage` made: `message_id` (FK, `ON DELETE CASCADE`, indexed), `position` (call order), `call_id` (LangChain run id), nullable `tool_id` (registry entry), `tool_name`, `phase` (`start`/`end`/`error`/`blocked`), JSON `args` (redacted; cut JSON text when too long), `args_truncated`, `result_preview` (untrusted text, at most 4 KB), `result_truncated`, `duration_ms`, nullable `approval` (JAN-254: `approved`/`denied`/`timeout`/`disconnected`/`unavailable` for a `confirmation="required"` call the user was asked about in chat, `NULL` otherwise), and `created_at`. Owned through the message's conversation; the ORM relationship deletes the rows with their message (and so with their conversation), since SQLite does not enforce the FK cascade. See [background workers runtime](background-workers-runtime.md) for the event shape.
- **Chat UI blocks (JAN-252):** `ConversationUIBlock` (`conversation_ui_blocks`) stores each validated UI block an assistant `ConversationMessage` rendered through `render_ui`: `message_id` (FK, `ON DELETE CASCADE`, indexed), `position` (render order), `block_id` (`blk_<12 hex>`), `block_type` (`card`/`table`/`chart`/`checklist`/`key_value`/`actions`/`image`), `schema_version` (the catalog version, `1`), JSON `payload` (the block as streamed, at most 8 KB), and `created_at`. Owned through the message's conversation; the ORM relationship deletes the rows with their message. See [background workers runtime](background-workers-runtime.md), "Chat UI blocks", for the catalog.
- **Generated images (JAN-253, `models_images.py`):** `GeneratedImage` (`generated_images`) is one picture the chat tool `generate_image` stored: `id` (`String(64)` primary key, the public URL-safe id in `/api/images/<id>`), `user_id` (FK `users`, `ON DELETE CASCADE`, indexed), `conversation_id` (FK `conversations`, `ON DELETE CASCADE`, indexed; nullable since JAN-359 for an image an unattended run made under *Allow everything*), nullable `message_id` (FK `conversation_messages`, `ON DELETE SET NULL`; the assistant message whose turn made it, set when the reply is saved), `prompt` (the full prompt as sent, including the style hint), `provider`, `model`, `path` (relative to `image_storage_dir`: `<user_id>/<id>.<ext>`), `mime_type` (`image/png`/`image/jpeg`/`image/webp`, sniffed), nullable `width`/`height` (read from the file header), `size_bytes` (for the per-user storage cap), and `created_at`. The bytes are a file, never a blob. The ORM relationship from `Conversation` deletes the rows with their conversation (SQLite does not enforce the FK cascade), and `ConversationService` removes the files. `Settings.image_provider` (nullable; `openai`/`gemini`/`openrouter`, `NULL` = off) and `Settings.image_model` (nullable; empty = the provider's default) configure the provider. See [background workers runtime](background-workers-runtime.md), "Chat image generation".
- **Memory compaction runs:** Compaction records include queued/running/completed/failed status, timestamps, and result summary.
- **Tracked topics:** Topics persist separately from reminders and memory facts with lifecycle state (including the pre-promotion `candidate` state), confidence, supporting evidence, pinning/manual confirmation, marker keywords, and user curation state.
- **Topic confirmation threshold:** Settings carry a default confirmation-mention threshold that seeds each user's `topic_tracking_preferences.min_confirmation_mentions` override.
- **Skill library:** `AgentSkill` rows (historical name) are one flat, instance-wide skill library applied to every surface; there is no per-agent assignment. Agent definitions, their skill links, and handoff runs no longer exist (dropped by `d5e8f1a2b3c4`).
- **Character profile:** `CharacterProfile` persists one versioned constitution per user, plus the optional free-text `additional_instructions` and `memory_instructions` (JAN-230).
- **Adaptive character state (JAN-301):** `CharacterProfile.state_envelope` (nullable JSON) holds the owner's allowed values and defaults per dimension. `models_character.py` (re-exported from `models`) adds `CharacterStateRecord` (`character_states`, one current state per user with a `revision`), `CharacterStateProposal` (`character_state_proposals`, inert proposals Janus filed from chat, `proposed`/`approved`/`rejected`), and `CharacterStateChange` (`character_state_changes`, the audit trail: actor, action, chat turn id, proposal id, previous and new state). All three cascade with their user (and are deleted explicitly on user deletion, since SQLite enforces no FK).
- **Runtime triggers:** `RuntimeTrigger` rows persist the normalized trigger identity (`trigger_id`, task-scoped `idempotency_key`, task, kind, source, and JSON payload), lifecycle status, private claim token, claim/completion timestamps, latest failure, and record timestamps. The unique `(task_id, idempotency_key)` constraint makes enqueue idempotent. New ingress rows carry the authenticated `user_id`; same-owner duplicates reuse the existing record, while cross-owner collisions return `409 Conflict` without exposing that record. API reads are owner-filtered and response schemas do not expose the JSON payload or claim token.
- **Trigger definitions (JAN-228):** `TriggerDefinition` (`trigger_definitions`) persists an owner's saved automation: `name`, `objective`, JSON `tool_ids`, `kind` (`manual`/`schedule`/`event`), JSON `schedule`, `timezone` (server default `UTC`), indexed `event_type`, `enabled`, `origin` (`user`/`system`/`agent`), `builtin_key`, indexed `next_run_at`, and `last_run_at`. Since JAN-235 it also carries the agent-proposal lifecycle: `proposal_status` (`TriggerProposalStatus`; `NULL` unless Janus drafted the row), `proposal_rationale`, `proposed_at`, `proposal_source`, `supersedes_id`, `approved_at`, `approved_by_user_id`, `approval_fingerprint`, `rejected_at`, `rejection_reason` (see [background workers runtime](background-workers-runtime.md#agent-proposed-definitions-jan-235)). Since JAN-363 event definitions carry JSON `event_filter` and `max_runs_per_hour`, and every row counts events its rate limit dropped (`rate_limited_count`, server default `0`, and `last_rate_limited_at`). `(user_id, builtin_key)` is unique, so each built-in exists at most once per user; the owner FK cascades on user delete.
- **Trigger runs ↔ definitions:** `RuntimeTrigger.definition_id` (nullable, indexed, `ON DELETE SET NULL`) links a run to its definition, `RuntimeTrigger.definition_name` (nullable, JAN-204, migration `d4f7b2c9e1a6`) snapshots the definition's name at enqueue time so the run stays a definition run after the definition is deleted, and `RuntimeTrigger.output` stores the run's raw final answer. The briefing's "today" result is read from these rows; there is no separate briefing cache.
- **Tool policies (JAN-229, JAN-255):** `ToolPolicy` (`tool_policies`) holds per-user overrides of whether a built-in capability is allowed in unattended runs (`unattended_allowed`, nullable boolean) and, for `confirmation="required"` entries, whether chat asks per call or withholds it (`chat_mode`, nullable string `"ask"`/`"always"`/`"off"`, JAN-306, JAN-359); `(user_id, tool_id)` is unique, a `NULL` column or a missing row means the registry default (unattended: allowed unless the entry is `confirmation="required"`; chat: ask every time), and a row with both columns `NULL` is deleted. `ToolPolicyMode` (`tool_policy_modes`, JAN-359) holds one row per user (`user_id` unique, `ON DELETE CASCADE`) with the blanket modes `unattended_mode` and `chat_mode` (non-null strings, `"per_tool"` (default) or `"allow_all"`); no row means both `per_tool`.
- **Self-evolution loop (JAN-320, `models_self_evolution.py`, migration `b7d1e4a9c2f6`):** `SelfEvolutionSettings` (`self_evolution_settings`, one row per user, `user_id` unique FK `ON DELETE CASCADE`): `enabled` (server default off), `routine_trigger_id` (`trig_...`), `routine_token` (Fernet-encrypted), `github_repo`, `production_base_url`, `updated_at`. `SelfEvolutionAction` (`self_evolution_actions`, FK `ON DELETE CASCADE`, indexed `user_id`/`action`/`subject`/`created_at`): one row per attempted action (`action` `issue_filed`/`job_started`/`feature_merged`/`release_merged`/`self_check`/`revert_opened`, `status` `pending`/`ok`/`failed`/`refused`/`duplicate`/`passed`, `subject`, `detail`, JSON `data`); the audit trail and the source of the loop's daily caps. A self-check's definition is an ordinary `TriggerDefinition` with `builtin_key` `selfevo.check:<action id>` (no schema change). See [background workers runtime](background-workers-runtime.md#autonomous-self-evolution-loop-jan-320).
- **Prompt-injection classifier (JAN-289, `models_safety.py`, migration `c3e5a7f9b1d2`):** `InjectionClassifierSettings` (`injection_classifier_settings`, one row per user, `user_id` unique FK `ON DELETE CASCADE`): `enabled` (server default off), `monthly_token_budget` (default 200,000), `usage_period` (`YYYY-MM`), `tokens_used`, `calls`, `updated_at`; counters from an earlier month read as zero. `InjectionClassification` (`injection_classifications`, FK `ON DELETE CASCADE`, unique `(user_id, content_hash)`, indexed `user_id`/`created_at`): one cached verdict per classified text window (`content_hash` = SHA-256 of the classifier version and the text, `suspected`, JSON `labels`, `model`, `created_at`); the text itself is never stored. Rows older than 90 days are pruned. See [Prompt-injection guardrails](llm-agent-safety.md#prompt-injection-guardrails-jan-127).
- **Trigger retry state:** `RuntimeTrigger.attempt_count` and `next_attempt_at` persist bounded retry policy state. Failed rows can be delayed, and the worker marks rows `exhausted` after the configured attempt limit.
- **Plan runtime states:** `PlanRuntimeState` rows persist an owner-scoped task graph snapshot, current graph node, plan status, JSON state, and optimistic revision. The unique `(user_id, task_id)` constraint gives each owner one resumable cursor per task; revision-guarded writes prevent a stale worker from overwriting a newer snapshot.
- **Runtime tool selections (JAN-300):** `RuntimeToolSelection` rows (`models_toolsets.py`, re-exported from `models`) record the brain-selected toolset of one plan step, unique per `(user_id, task_id, step_id)`: the offered `tool_ids` (`NULL` = every authorized toolbox), `source` (`selected`/`persisted`/`fallback`/`unnarrowed`), `reason`, the raw `proposed_tool_ids`, `trimmed_tool_ids`, and chat's `widened_tool_ids`. A retried or resumed step reuses its task's row; deleting a conversation deletes its rows (`task_id = chat-conversation-<id>`).
- **App shell preference:** `User.ui_version` persists which dashboard shell the account renders (`v1` classic glass, `v2` terminal, `v3` rusty console). It is a plain string, non-null with a `v1` server default, so every existing and new account starts on the classic shell and adding a shell needs no migration — only the Pydantic `Literal` widens.
- **Managed MCP registry:** `MCPServer`, `MCPDiscoveredTool`, and `MCPCredential` persist owner-scoped HTTP MCP connection metadata, advisory discovery snapshots, per-tool enablement, health state, and encrypted OAuth tokens or an owner-supplied static bearer token (`token_type = "static"`, no refresh token or expiry, JAN-342; no schema change). Credentials are deleted with their server and are never part of API serialization.

## Migration Requirements

- Bug fixes for schema/startup issues must ship with regression tests against realistic existing-database scenarios.
- Significant schema changes should update this spec or a more focused child spec before implementation.
- Existing local databases must continue to upgrade safely through Alembic.
- Every migration must run on both SQLite and PostgreSQL. CI's `migration-tests` job runs the chain, a full downgrade/upgrade round trip, and an enum-parity check against a PostgreSQL service (`tests/test_postgres_migrations.py`). PostgreSQL-specific rules:
  - Widening a native enum (`sa.Enum` without `native_enum=False`) needs `ALTER TYPE <name> ADD VALUE IF NOT EXISTS '<VALUE>'` on PostgreSQL; a batch `alter_column` does not change the type there. PostgreSQL cannot drop enum values, so the downgrade leaves them in place.
  - A native enum type that already exists (or is created explicitly with `.create(bind, checkfirst=True)`) must be referenced as `postgresql.ENUM(..., create_type=False)`; `sa.Enum` ignores `create_type`.
  - Native enum types store the enum member *names* SQLAlchemy writes (`RUNNING`, not `running`).
  - Identifiers are capped at 63 characters, and `batch_alter_table(recreate="always")` must stay SQLite-only.
- Planner migrations must preserve the separation between imported read-only planner records and Janus-owned writable planner records.
- Migrations must preserve data ownership and not orphan persisted history such as memory facts, trigger runs, or plan state. A migration that deliberately drops a feature's data (as `d5e8f1a2b3c4` does) must say so in its docstring and in this list.
