# E2E Code Map

Scope: Playwright end-to-end specs for the dashboard, run against a real backend on a throwaway SQLite database (see `../playwright.config.ts`).

## Responsibilities

- exercise user-facing flows through a real browser against a real (but isolated, disposable) backend instance
- provision and reuse a single logged-in admin session across specs via a shared storage state
- keep specs independent of each other and of their order (JAN-336): a spec whose data is per user runs as its own throwaway user, and a spec that changes an instance-wide setting resets it in `afterEach`; no assertion depends on global counts or empty states of the shared admin's data

## Running e2e runs side by side

Each checkout gets its own data dir and port, so parallel worktrees do not share a database or fight over a port. Two runs from the same checkout at once are not supported: the second run's setup deletes the first one's data dir. Overrides, all read by `env.ts`:

- `E2E_PORT` -- backend port (use it if two checkouts happen to hash to the same port, or the port is taken)
- `E2E_DATA_DIR` -- data dir for the database, XDG dirs, and storage state; it is deleted at the start of every run, so point it at a throwaway path (a non-empty directory that a previous e2e run did not create, i.e. one without the `.janus-e2e-data-dir` marker, is refused rather than wiped)
- `TMPDIR` -- parent of the default data dir

For example: `E2E_PORT=8642 TMPDIR=/tmp/my-run npm run test:e2e`.

Confirmations are in-app `ConfirmDialog`s (JAN-292), not browser dialogs: use `answerConfirm` from `helpers.ts` (or click the button inside `getByRole('dialog', { name })`) instead of handling `page.on('dialog')`. A spec that changes global settings, like `setCloudUtilityModel`, resets them in `afterEach`.

## Test isolation (JAN-336)

All specs share one backend and one database, and run in file order. A test therefore never relies on what an earlier spec did or did not leave behind:

- Per-user data (memory facts, compaction runs, topics, dashboard widgets and local planner items, mail and rules, trigger definitions and runs, conversations and delegations, briefing runs, the app shell, wiki pages) belongs to a throwaway user: `test.use({ asThrowawayUser: true })` signs `page` in as a fresh one before any hook runs (`account` names it, so `runBackendPython(snippet, args, { as: account.username })` seeds for it). Tests that share seeded data create one user in `beforeAll` with `createThrowawayUser(adminRequest, ...)` and `signInAs` it in `beforeEach`. Throwaway users are never cleaned up; nothing reads across users.
- Instance-wide settings (backend and utility model, semantic search, image generation, integrations, mail ingestion limit, self-evolution, the injection classifier, Google OAuth client) can only change on the shared admin; such a spec resets them in `afterEach` (through `adminRequest` when `page` is a throwaway user), so a failure half-way leaves nothing behind.
- Assertions on the shared admin are scoped to what the test created (its stamp, its ids), never to global counts or empty states.
